# SKILL 最佳实践

## 一、SKILL 的定位与价值

- **SKILL** 是模块化能力扩展包：一个 skill 对应一个 `SKILL.md` 及可选附件（脚本、模板等），作为「通用 Agent 的扩展包」被加载。
- **核心价值**：只在被调用时加载，不持续占用上下文，相比把大段说明塞进 system prompt 更省 token、更易维护。
- **命名约定**：目录名与 skill 名称统一使用**中划线**（如 `admin-data-source-assistant`、`sql-generator`），便于路由与引用。

---

## 二、元数据：name 与 description

### 2.1 必填 frontmatter

```yaml
---
name: your-skill-name
description: 一句话说明「做什么、何时用、边界在哪」。
---
```

- **name**：与目录名一致，中划线命名，用于路由与跨 skill 引用。
- **description**：是**路由与决策的核心依据**，模型据此决定「是否调用本 skill」。

### 2.2 description 最佳实践（面向路由）

description 应能回答三类问题，便于主智能体或路由逻辑正确选择：

| 问题 | 建议写法 |
|------|----------|
| **什么时候用？** | 明确适用场景、关键词、前置条件。 |
| **什么时候不用？** | 明确不适用场景，或写「不负责 X，该部分由 Y skill 负责」。 |
| **输出什么？** | 简要说明交付物（如「生成 SELECT 并执行」「返回模型详情供 sql-generator 使用」）。 |

**推荐句式**：  
「专职……。适用于……。不负责……，该部分由 **xxx-skill** 负责。关键词：A、B、C。」

- **正面**：列出触发本 skill 的关键词与场景。
- **负面**：列出「别在 X 场景调用我，此时应用 Y skill」，可显著减少误触发（业界实践表明相似 skill 若无负面说明，触发率可能下降约 20%）。
- **关键词**：便于检索与路由，逗号分隔。

## 三、正文结构建议

### 3.1 职责与边界（强烈建议）

- **职责**：用列表写清「本 skill 负责做什么」，包括输入来源（如「由 data-information-exploration 提供」）、输出/交付物。
- **不负责 / 非职责**：明确不做的内容（如「不生成 SQL」「不执行 DDL」）。
- **边界**：数据与安全边界（如「仅查询白名单表」「仅生成 SELECT」）。

这样既方便模型决策，也方便人类评审和后续扩展。

### 3.2 工作流程 / 步骤说明

- 用**有序步骤**写出主流程（如：1. 确认输入 2. 生成 SQL 3. 执行 4. 错误处理）。
- 关键步骤注明**依赖**（如「若缺失则说明需先由 xxx skill 获取」）和**工具调用**（如 **tool_execute_sql_on_data_source**）。
- 复杂分支可单独设「细则」或「错误处理」小节。

### 3.3 模板与格式

- 若输出有固定格式（报告、摘要、导出结构），**把模板直接写在 SKILL 内**，在触发时随 skill 加载，而不是全部塞进 system prompt，以节省 token 并降低延迟。
- 在 SKILL 中写明「必须使用 Markdown」「禁止 JSON」等格式约束，避免模型自由发挥导致解析困难。

### 3.4 工具与依赖

- 用**粗体**标出工具名（如 **tool_execute_sql_on_system_db**），并在合适位置说明参数与使用场景。
- 跨 skill 协作时，明确写出「由 **xxx-skill** 负责」「交付给 **yyy-skill**」，避免职责重叠或遗漏。

---

## 四、关键流程与显式指令

- 默认完全依赖模型「自己决定用哪个 skill」在关键路径上不够稳定。
- 对**关键流程**（如必须先选模型再生成 SQL），建议在 MEMORY 或上层说明中**显式写出**：「先使用 data-information-exploration 获取模型，再使用 sql-generator 生成并执行 SQL」。
- SKILL 内部也可在「工作流程」第一步写：「若未获得模型详情，须先由 data-information-exploration 获取」，与显式指令形成双保险。

---

## 五、负面例子与相似 Skill 区分

- 当存在多个相似 skill（如多个「助手」、多个「分析」）时，**必须在各自 SKILL 中写清「何时不用我」**。
- 示例：「不负责获取模型列表或选模型，该部分由 data-information-exploration 负责。」
- 可增加简短负面示例（如「用户仅问数据源列表时，不要调用本 skill 做 SQL 生成」），减少误触发。

---

## 六、安全与防护

- **数据与权限**：在「边界」中明确可访问的表、可执行的操作（如仅 SELECT、仅白名单表）。
- **密钥与配置**：API 凭证、数据库密码等不写入 SKILL 正文，使用配置/密钥管理（如 domain_secrets），模型侧只看到占位符或说明。
- **网络与外部调用**：若 skill 涉及外网调用，应在平台层做白名单或开关控制，并在 SKILL 中说明使用条件。

---

## 七、与 MEMORY 的配合

- **MEMORY.md** 描述智能体整体角色与能力范围，并列出各 skill 的**名字与一句话用途**（如「使用 skill：admin-data-source-assistant」）。
- MEMORY 中 skill 名称与 SKILL 的 **name**、目录名保持一致（中划线），便于主智能体路由到正确 skill。
- 可在 MEMORY 中简要写出「先 A 后 B」的固定流程，与各 SKILL 的「职责与边界」「工作流程」一致。

---

## 八、检查清单（编写/评审时）

- [ ] **name** 与目录名一致，且为中划线命名。
- [ ] **description** 包含：何时用、何时不用、输出什么；含关键词。
- [ ] 有**职责**与**不负责/边界**说明。
- [ ] 工作流程步骤清晰，依赖与工具调用已标明。
- [ ] 与其它 skill 的协作关系写清（谁提供输入、谁接收输出）。
- [ ] 固定输出格式已内置于 SKILL（模板/示例），并注明格式约束。
- [ ] 安全与数据边界已说明（表、操作类型、凭证处理）。
- [ ] MEMORY 中引用本 skill 的名称与 name 一致。
